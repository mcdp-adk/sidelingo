# 运行一台小型自托管 Git 服务器

本指南介绍如何为五到二十人的团队搭建一台**自托管 Git 服务器**。假设你有一台拥有公网 IP、约 20 GB 可用磁盘空间的 Linux 机器。

## 为什么要自托管

托管服务很方便，但有些团队需要把源代码保存在自己掌控的硬件上。常见原因包括：

- 合同禁止把代码存放在第三方。
- 与互联网完全隔离的内网。
- 希望避免随团队扩大而增长的按席位计费。

如果以上都不适用，把维护所花的时间算进去，托管服务几乎总是更便宜的选择。

## 选择软件

对于这种规模的团队，有三个现实的选项：

| 方案 | Web 界面 | 内存 | 说明 |
| --- | --- | --- | --- |
| 纯 SSH + Git | 无 | 约 0 MB | 没有拉取请求，也没有议题跟踪 |
| Gitea | 有 | 约 150 MB | 单个二进制文件，升级简单 |
| GitLab CE | 有 | 约 4 GB | 内置 CI，运行开销大 |

对大多数小团队来说，**Gitea** 恰到好处：它有拉取请求和议题，却能在双核虚拟机上轻松运行。

## 准备机器

创建一个专用用户，确保服务器永远不以 root 身份运行：

```bash
sudo adduser --system --group --home /srv/git git
sudo mkdir -p /srv/git/{data,repos}
sudo chown -R git:git /srv/git
```

然后只开放需要的端口。基于 SSH 的 Git 使用 22 端口，Web 界面则放在 443 端口的反向代理之后。

## 安装 Gitea

下载发布版二进制文件，校验其校验和，并将其安装为 systemd 服务。把二进制文件放在 `/usr/local/bin` 下，这样升级只需替换一个文件。

1. 下载适合你架构的二进制文件。
2. 将其 SHA-256 值与发布页上的值进行比对。
3. 把示例单元文件复制到 `/etc/systemd/system/`。
4. 运行 `systemctl enable --now gitea`。

服务首次启动时，Web 安装程序会要求选择数据库。二十个用户用 SQLite 就够了；只有出现锁争用时才需要换成 PostgreSQL。

## 放到 HTTPS 之后

永远不要通过纯 HTTP 暴露 Web 界面。Caddy 之类的反向代理会自行申请并续期证书：

```text
git.example.com {
    reverse_proxy localhost:3000
}
```

重新加载代理后，访问站点并确认出现了锁形图标，然后再邀请其他人。

## 备份

没有备份的 Git 服务器就是单点故障。Gitea 自带 `dump` 命令，可以把数据库、仓库和配置写入同一个归档文件。

- 通过 cron 任务**每晚**运行一次导出。
- 把归档复制到另一台机器或对象存储。
- 至少保留**七份每日**和**四份每周**副本。

> 从未恢复过的备份只是一种希望。每个季度都把一份备份恢复到临时机器上试一试。

## 升级

每次升级前都要阅读发布说明，尤其是标有*破坏性变更*的部分。常规流程很短：停止服务、执行导出、替换二进制文件，再重新启动服务。如果 Web 界面显示迁移提示，请等它完成后再让任何人推送。

## 何时该换方案

当服务器需要的关注超过它所存放的代码时，自托管就不再划算了。以下迹象说明是时候重新考虑了：

- 每月花在维护上的时间超过一个下午。
- 团队需要你无法提供的 CI 运行器。
- 团队里没有人愿意为这台服务器值班。

到了这一步，迁移到托管服务通常只需一天，因为每种方案都能导入普通的 Git 仓库。
